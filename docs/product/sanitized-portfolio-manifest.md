## Relative-date policy

The builder accepts exactly one aware `as_of`, converts it to UTC, and derives all timestamps from fixed offsets:

- Submission deadlines: +20 hours, +2 days, +5 days, +14 days, +5 days, +7 days, +2 days.
- Audition deadline: exactly two days after each Submission deadline.
- Tracked booking callback: exactly six days after its Submission deadline.
- Shoot start: the UTC calendar date twenty days after each Submission deadline.
- Shoot end: five days after shoot start.
- Planned Submission timestamps: −1 day, −12 hours, and −3 days from `as_of`.

Naive datetimes are rejected. Equivalent timezone representations of the same instant serialize identically.

Persisted temporal fields are stable across ordinary seed reruns. A new `as_of` affects existing
portfolio records only after an explicit reset/reseed. Ordinary updates compare and modify only the
non-temporal manifest-owned allowlist; they preserve submission and audition deadlines, callback date,
and shoot start/end dates. `--reset --execute` followed by a normal `--execute` deliberately recreates
those timestamps from the new run's single timezone-aware `as_of`.

## Opportunity persistence boundary

The seed owns only: source type, role, project, description, project/role type, union, location,
audition type, open status, acting classification, initial visibility/review state, confidence,
source reliability, exact ownership metadata, bounded role/production details, and the five temporal
fields listed above. Ordinary updates do not overwrite enrichment scores, priority, risk and quality
explanations, demographic enrichment, watch-list matches, workflow relationships, or other derived state.

Direct ORM construction is intentional for this bounded seed: the immutable manifest supplies all
required model invariants, while normal Opportunity workflows may enrich records or own commits. The
seed script remains the sole transaction owner and commits the seven records together. Reset fails closed
when Submission, Calendar, journal, recommendation, feedback, or callback dependencies exist; the later
full dependency-aware reset must remove those records first.

## Career-targeting persistence boundary

The seed persists CastingGoal `6926a996-8c5c-52d4-9687-fcd697aa0db2` with the
manifest title, `TV` goal type, target archetypes, role types, project types, markets,
High priority, and Active status. `WorkflowConnectorService.after_casting_goal_saved`
derives its actor-owned WatchList; the seed does not assign the WatchList UUID or invent
independent matching fields. Existing global refresh then applies normal match fields to
non-demo Opportunities.

CareerMemory `d7ac3ea7-3ebe-5529-b22b-5eafdb4d9a6e` owns only current focus,
career goals, stretch archetypes, preferred project types, preferred markets, and the
fictional actor relationship. Career/executive notes and unavailable dates remain outside
the seed allowlist. A non-committing CareerMemory primitive allows the seed script to own
the single commit while existing public methods retain their previous commit behavior.

Scoped career-targeting reset deletes the derived actor-owned WatchList, CastingGoal, and
CareerMemory in that order. The fictional profile, travel preferences, and seven
Opportunities remain. Active WatchList context is now available to the command-center
scoring assembler; it does not currently assemble `career_goal_matches`, so strategic-
stretch goal scoring remains neutral. Submission and recommendation-feedback inputs also
remain neutral until later tasks. The absent `(actor_profile_id, title)` WatchList unique
constraint leaves a deferred concurrent-save duplication risk.

## Sanitized-content rules

- All names, projects, roles, locations, identity values, and narrative text are fictional.
- Opportunity fields inspected by legacy cleanup contain none of the standalone trigger words `demo`, `example`, `sample`, or `test`.
- No `example.com` or invented public URL is used; Opportunity URLs remain absent in the manifest.
- Every Opportunity exposes exactly `source_metadata.portfolio_seed.namespace = sanitized-portfolio-v1` and `is_demo_data=False`.
- The manifest contains no contact details, credentials, asset paths, private notes, or real-user sentinels.

## Selected transaction-composition strategy

The eventual seed remains all-or-nothing and the script remains the only commit owner.

1. Use existing Option A primitives where they are already non-committing: WorkflowConnectorService, WatchList refresh, ActorWorkEventService, and JournalService.record_once.
2. Before records requiring them are persisted, make two narrow Option B extractions: CareerMemory create/apply and Submission create. Existing public methods must keep their current commit behavior and delegate to the extracted primitive.
3. Construct deterministic Opportunity, AgentRecommendation, and RecommendationFeedback roots only after validating manifest identity and relational invariants. Feedback learning analysis is deferred; actor-interest scoring reads RecommendationFeedback directly.
4. Flush only when generated primary/foreign keys are needed, apply all derived workflow writes, then perform one final script commit. Any exception rolls the whole graph back.

No significant repository-wide transaction refactor or unit-of-work abstraction is justified. If either narrow extraction proves behaviorally larger than the inspected methods, defer the corresponding CareerMemory or Submission subtree rather than permit partial commits.

## Dry-run projection

`project_manifest_dry_run` is pure and accepts caller-supplied existing, changed, and removal ID sets. It reports create/update/unchanged/remove counts in stable type order. With the already-created fictional ActorProfile and TravelPreference and no other records, the root projection is:

```text
ActorProfile            create 0 update 0 unchanged 1 remove 0
TravelPreference        create 0 update 0 unchanged 1 remove 0
CastingGoal             create 1 update 0 unchanged 0 remove 0
CareerMemory            create 1 update 0 unchanged 0 remove 0
Opportunities           create 7 update 0 unchanged 0 remove 0
Submissions             create 3 update 0 unchanged 0 remove 0
AgentRecommendation     create 1 update 0 unchanged 0 remove 0
RecommendationFeedback  create 1 update 0 unchanged 0 remove 0
```

Derived rows are separately projected as one WatchList, three histories, ten Calendar events, three AuditionJournal entries, and three ActorJournal entries. Task 4A does not query or write the database to produce this projection.

## Cleanup implications

Before deletion, reset must resolve all root and derived ownership IDs. Calendar and both journal types must be deleted before Submission and Opportunity parents because their `SET NULL` links would otherwise erase ownership evidence. Feedback precedes recommendation; Submission associations precede Submission; goal-derived WatchList precedes CastingGoal. Opportunities precede the fictional ActorProfile only after their protected Submission history has been removed. The dedicated sanitized database and safety gate remain the primary isolation controls.
